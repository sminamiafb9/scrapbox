# AGENTS.md

このファイルは、開発Agentがリポジトリ内で作業する際の基本的な指針と、参照すべきドキュメントの所在を示します。
実装に着手する前に、以下の指針と関連ドキュメントを確認してください。

## 1. ドキュメントの参照先

開発内容に応じて、次のドキュメントを参照してください。

- `README.md`
  - プロジェクト全体の方針、共通ルール、開発時に遵守すべき事項を確認する。
- `docs/`
  - システムアーキテクチャや設計上の背景、構成要素間の関係を確認する。
  - 実装がアーキテクチャの方針と整合していることを確認する。
- `steering/`
  - 実装計画やWBS、開発対象の具体的な作業内容と順序を確認する。
  - 作業対象のPhase、PR、タスクおよび依存関係を確認する。

ドキュメント間で矛盾がある場合は、独断で解決せず、矛盾点と影響をユーザに報告して確認してください。実装に必要な情報が不足している場合も、重要な仕様を推測で確定しないでください。

## 2. 開発時のGit運用ルール

以下のルールを必ず遵守してください。

- **`main` に直接変更を加えたり、pushしたりしてはいけません。**
- **機能開発や修正作業を開始する際は、必ず作業用のブランチを作成してください。** `main` などの共有ブランチ上で直接作業しないでください。
- 作業内容に応じて適切なブランチ名を付けてください。
- 変更は機能や責務に応じて適切な単位にまとめ、レビュー可能な状態にしてください。
- `main` をターゲットとするPRを作成したら、PRのURLと概要をユーザに報告してください。
- PRを作成した後、ユーザの指示なくPRをマージしてはいけません。

## 3. 実装の進め方

1. `README.md`、関連する `docs/`、`steering/` のドキュメントを確認する。
2. 作業内容、依存関係、受け入れ条件を把握し、不明点や重要な仕様の不足があればユーザに確認する。
3. `main` の最新状態を基準に作業用ブランチを作成する。
4. 指定されたタスクの範囲内で実装する。
5. 変更に対応するテスト・検証を実施する。
6. 差分を確認し、不要な変更や機密情報が含まれていないことを確認する。
7. 変更をコミットし、`main` をターゲットとするPRを作成する。
8. PRの作成をユーザに報告する。

## 4. 実装と品質に関するルール

- 既存の設計・実装方針を尊重し、タスクの範囲を超えた変更を避けてください。
- 実装計画やWBSで定義された作業単位を尊重してください。
- 関連性の薄いリファクタリングや仕様変更を同じPRに混在させないでください。
- 既存コードの命名規則、構成、依存関係、コードスタイルに合わせてください。
- 新しい依存ライブラリを追加する場合は、必要性を検討し、依存関係の定義も更新してください。
- テストや検証を実施した場合は、その内容と結果を明確にしてください。検証できていない事項を検証済みとして報告してはいけません。
- 実装に伴ってドキュメントが古くなる場合は、必要な範囲で更新してください。
- APIキー、トークン、パスワード、個人情報などの機密情報をコード、ログ、コミット、PRに含めないでください。

## 5. Notebook / Databricks開発時の注意

- 既存のNotebook構成とプロジェクト内の実行方式に従ってください。
- Notebook間の入力・出力契約を明示し、既定のインタフェースを独断で変更しないでください。
- Notebookの実行結果や不要な生成物を差分に含めないよう確認してください。
- Databricks環境でしか実行できない検証は、その制約を明記し、ローカルで検証可能な範囲と区別して報告してください。

## 6. PR作成時の報告

PRを作成した際は、ユーザに次の内容を報告してください。

- PRのURL
- 変更概要と対応タスク
- 実施したテスト・検証とその結果
- 未検証事項や既知の課題

PRはレビュー可能な状態で作成し、ユーザの指示なくマージしないでください。
